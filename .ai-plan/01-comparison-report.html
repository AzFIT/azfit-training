Architecture patterns, TypeScript strictness, and technical debt analysis

▶ TypeScript Strictness

  • CRITICAL Portal: Heavy any usage in DB layer undermines type safety
  • HIGH Portal: Duplicate Client interfaces across files — type definitions diverged
  • HIGH Portal: TS 5.9 with lax config — strict mode not enforced
  • MED Training: TS 5.3 (older) but more consistent typing patterns
  • MED Training: Service layer coupled to store (workoutApi.ts calls useAppDataStore.getState())
  • LOW Both: No strict null checks enabled, implicit any allowed in places

▶ Component Organization

  • CRITICAL Portal: ClientProfile 1000+ lines, 7 inline tabs — unmaintainable
  • CRITICAL Portal: AllInOneProgramPage 90KB — massive monolith
  • CRITICAL Training: ClientProfilePage 2000+ lines, 13 inline tabs — worse
  • CRITICAL Training: ProgramWizardPage 2478 lines — most complex page
  • HIGH Portal: ProgramBuilder 33KB single file
  • MED Training: Better directory structure (services/, utils/, stores/)
  • LOW Both: No code splitting — every page in main bundle

▶ State Management Patterns

Portal (Flat Store)

Simple Zustand store with flat structure. Dual persistence to Supabase + localStorage. Manual cache invalidation with useEffect hooks. Easier to understand but doesn't scale well.

Flat Structure Manual Cache Dual Persistence
Training (Normalized Store)

Normalized Zustand store with selective persistence. Entities stored by ID for O(1) lookups. Derived selectors compute view models. Offline-first capable. Better for complex data relationships.

4-phase approach to unifying both repositories

Foundation Cleanup (Week 1)

Prepare the azfit-training codebase before merging any new features. Focus on structural fixes that affect the entire app.

Replace HashRouter with BrowserRouter Remove react-router v7 Split ClientProfilePage into tabs Split ProgramWizardPage into steps Replace global counters with UUID Remove hardcoded demo data Consolidate hardcoded colors into Tailwind config

Port Unique Portal Features (Week 2-3)

Bring over the client portal's unique features, adapting them to Training's architecture patterns (TanStack Query, normalized store).

AdminDashboard page + coach management AI Chat Assistant (offline, @-commands) Excel/PDF export (extract from AllInOneProgramPage) Program Matcher algorithm Client Intake Wizard (4-step) Supabase RLS + multi-tenant patterns
3

Security Hardening (Week 3-4)

Address all critical security issues before production deployment. Both repos have significant security debt.

Implement Supabase Auth (replace custom) Remove base64 password hashing Remove dev auto-login backdoor Add Row Level Security policies Add input sanitization Rate limiting on auth endpoints
4

Testing & Optimization (Week 4-5)

Add testing infrastructure, error boundaries, code splitting, and performance optimizations.

Install & configure Playwright Add React Error Boundaries Code splitting (React.lazy + Suspense) Bundle analysis and optimization gh-pages deploy script E2E test coverage for critical flows

Risk Mitigation

High Risk: File Size Refactoring

Splitting 2000+ line files risks introducing bugs. Approach: extract one tab at a time, test after each extraction. Keep the original file as a composite wrapper during transition.

Medium Risk: Data Model Differences

Portal and Training may have different DB schemas. Audit Supabase tables from both projects (fodvpcwlpwfgmgvfczvb vs mhwrqkfttjbxryhlmhti) before merging.

Medium Risk: Auth System Migration

Switching from custom auth to Supabase Auth will require UI changes and data migration. Plan a migration path for existing user accounts if any exist in the target Supabase project.

Low Risk: Styling Inconsistencies

Both use Tailwind 3.4 with similar dark theme. Consolidating hardcoded colors into the Tailwind config is mechanical work with low regression risk.
